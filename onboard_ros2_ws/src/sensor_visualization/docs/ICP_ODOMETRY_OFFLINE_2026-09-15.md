## Current node and data flow

`rtabmap_odom/icp_odometry` is launched by
`launch/lidar_odometry.launch.py`.

```text
/scan (sensor_msgs/LaserScan, lidar_link)
  -> rtabmap_odom/icp_odometry
  -> /odom (nav_msgs/Odometry, odom -> lidar_link)
  -> /odom_info (rtabmap_msgs/OdomInfo)
```

The original launch remaps `scan -> /scan` and `odom -> /odom`. It uses
frame-to-frame (`Odom/Strategy=1`) 2D libpointmatcher ICP, 0.20–8.0 m scan
range, 0.03 m voxels, 0.15 m correspondence distance, and a 0.70 required
correspondence ratio. `publish_null_when_lost=false` deliberately makes stale
odometry visible instead of publishing false zero poses.

## Root cause

The baseline fails on a scan with 480 correspondences and ratio 0.646030:

```text
Cannot compute transform (cor=480 corrRatio=0.646030/0.700000 ...)
```

That scan is rejected solely because 0.646 is below the configured 0.70.
Frame-to-frame motion guessing then has no previous accepted transform, so
libpointmatcher receives a null guess. Every later scan fails with:

```text
RegistrationIcp cannot do registration with a null guess.
```

This is not a LiDAR outage, timestamp discontinuity, missing-TF error, or
duplicate-odometry issue. The first failure is an overly strict acceptance
threshold; the null-guess cascade is its consequence.

## Controlled experiments

| Test | Parameter change | Result | Coverage | Failure | Notes |
|---|---|---|---:|---|---|
| Baseline final motion | None (`CorrespondenceRatio=0.70`) | FAIL | 4.695/9 s | `1789489512.0576` | ratio 0.646 rejected; 76 null-guess errors |
| Ratio 0.30 final motion | Ratio only: 0.70 -> 0.30 | PASS | 8.791/9 s | none | 89 odom outputs/90 scans; trajectory 0.152 m |
| Ratio 0.50 final motion | Ratio only: 0.70 -> 0.50 | PASS | 8.791/9 s | none | same trajectory; minimum observed useful ratio 0.529 |
| Ratio 0.50 first pulse | Same candidate, earlier 0.30 s pulse | PASS | 9.793/10 s | none | trajectory 0.0577 m |
| Ratio 0.50 middle pulse | Same candidate, intermediate motion | PASS | 9.790/10 s | none | trajectory 0.0290 m |

The 0.50 candidate is preferred over 0.30: it is the smallest change from the
baseline that retains a measured margin below the minimum accepted moving-scan
ratio (0.529), without relaxing translation, rotation, range, voxel, backend,
or reciprocal-correspondence guards.

The final replay estimates `dx=-0.152 m`, `dy=-0.007 m`, and yaw `+0.005 rad`.
The negative x sign describes the installed LiDAR frame orientation; it must
be corrected by a measured `base_link -> lidar_link` extrinsic before the
odometry is interpreted as robot-forward motion. The magnitude is plausible,
but the normalized vendor command is not yet calibrated as exactly 0.10 m/s.
