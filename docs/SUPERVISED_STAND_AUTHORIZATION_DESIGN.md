# Supervised stand-only authorization — design review

Status: OFFLINE DESIGN ONLY. No production authorization gate changed.
No new console action is installed. No robot commands were sent during this work.

## Evidence and blocker

The acquisition-only experiment submitted a request, maintained fresh feedback,
zero software velocity and a closed joint-send gate. Raz reported no physical
motion. Release returned the local request state to NOT_REQUESTED. This proves
only the observed acquisition-only behavior, not authoritative ownership or
safe standing. Packet absence was not independently captured on the wire.

Production HardwareInterface::IsControlAcquired() remains false: the available
SDK does not provide an authoritative ownership acknowledgment. RequestStand,
RequestRLControl and the joint gate therefore remain blocked. Do not remove
this guard or equate a successful ControlGet call with confirmed ownership.

## Proposed permission, not ownership

A future explicitly reviewed stand-test permission must be separate from
ownership reporting, which remains OWNERSHIP_UNCONFIRMED throughout.
It must authorize only the existing StandUpState controller, never RL,
nonzero policy input, RobotStateInit, or arbitrary joint output.

Proposed operator sequence (NOT currently implemented commands):

1. Explicit acquisition request in a new session, after passive checks.
2. `authorize_stand_test`: record a one-use supervised authorization; no packets.
3. Separate `stand`: queue the existing stand transition; still no send permission.
4. Open the restricted output gate only after actual authorized StandUp entry.

Preconditions: current acquisition session, fresh finite SDK feedback, zero
normalized velocity, idle state, closed joint gate, reviewed fresh passive
health information, physically secured robot, operator present and E-stop ready.
Human preconditions require explicit current acknowledgment, not defaults.
Absence of decoded fault fields must not be described as proof of no faults.
State 98 remains undocumented; an observed blue light is not ownership evidence.

## State and timing proposal

LOCKED -> ARMED -> PENDING -> ACTIVE -> REVOKED

- ARMED and PENDING never permit joint transmission.
- Arming expires after 5 seconds; duplicate arming cannot extend it.
- ACTIVE permits only finite output from the existing StandUp controller.
- A proposed 10-second active observation budget is not a vendor guarantee.
- Existing stand parameters specify two 1.5-second trajectory phases, approximately
  3 seconds total. Policy and trajectory parameters remain unchanged.
- The gate must recheck conditions at each send under the existing synchronization.
- A revoked grant cannot resume after telemetry recovers. A fresh acquisition
  session and new explicit authorization are required; old session IDs fail.
- RL and nonzero velocity remain blocked even while the stand grant is active.

Revoke on stop, release, shutdown, stale feedback, health failure, session change,
lost supervision, nonzero input, wrong output producer or invalid joint values.
This is a specification of permission, NOT a complete physical abort controller.

## Unresolved safety requirement before production integration

Standing requires joint packets generated by the existing stand controller;
it cannot be achieved with zero joint transmission. This differs from manually
implementing a joint trajectory, which is not proposed here.

Closing a send gate or releasing ownership while supporting the robot's weight
may cause a fall or posture change. Acquisition-only release did not test this.
Before hardware use, review the exact stand abort/timeout/handoff sequence and
vendor behavior under load. Do not assume immediate torque removal is safe.
The proposal cannot keep authorization indefinitely or automatically fall back
to another unreviewed controller. Expiry is a mandatory supervised handoff
boundary whose physical behavior remains a hardware-review blocker.

Future implementation must preserve zeroing input, clearing pending requests,
stopping/joining workers, serialized send exclusion and release ordering.
It must not call RobotStateInit, claim ownership confirmation, modify ONNX,
or introduce motion modes. This work does not authorize that implementation.

## Isolated executable specification

Files: tests/supervised_stand_review_model.hpp and
tests/supervised_stand_review_test.cpp. Neither is included by production targets
or CMake. The model imports no SDK, socket, ROS or policy code. Conditions are
synthetic inputs; they do not read actual robot health or enforce thread safety.
Logical tests are not proof of runtime integration, real timing, or physical safety.

Compile/run offline:

```sh
g++ -std=c++17 -Wall -Wextra -Werror -pedantic tests/supervised_stand_review_test.cpp -o /tmp/lite3_supervised_stand_review_test
/tmp/lite3_supervised_stand_review_test
```

Checks cover default denial, missing preconditions, deadline boundaries,
duplicate authorization, acquisition-session isolation, no early output,
stand-only producer restriction, no RL/velocity permission, revocation,
no automatic recovery, invalid output and honest unconfirmed ownership.

## Teaching notes for Raz

- Simple: permission to try standing is not evidence the robot accepted ownership.
- Engineering: acquisition state, operator authorization and output permission
  are separate states. A queued request cannot open the send gate; the actual
  controller transition and send-time checks must agree.
- Project-specific: the current Lite3 guard correctly prevents stand because
  ownership is unconfirmed. This document proposes a narrower supervised test
  capability for separate review, not an invisible bypass. Stable standing and
  safe handoff still require secured hardware validation later.

Next step: review the supervised permission and physical abort/handoff design;
obtain separate approval before changing production authorization code.
